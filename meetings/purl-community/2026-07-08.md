- Introductions.
- Summary
  - The team discussed project updates involving library expansions and API enhancements.
  - A consensus was reached to change some PURL test terminology and tag version 1.1 of the purl-spec repository when those changes are implemented.
  - Participants analyzed the difficulty of identifying internal components versus public software. Discussions centered on using existing qualifiers instead of creating new internal package types for organizational tracking.
  - The group concluded that provenance issues stem from organizational process failures rather than technical limitations. Successful tracking requires building team accountability and dynamic configuration strategies within development platforms.
- **Participant Introduction and Meeting Context**: Keith Grant from the Red Hat product security department joined the meeting to observe and learn about improving internal usage of Package-URLs to support vulnerability information accuracy. Michael Herzog confirmed that he added several test items to the agenda, and participants confirmed they were ready to proceed with the meeting.
- **Clearly Defined Project Updates**: Philippe Ombredanne provided updates on the Clearly Defined project hosted by the Open Source Initiative, noting that the project runs 55 million scans on open-source packages and is adding support for Package-URLs. This update includes creating a library to convert Clearly Defined coordinates to Package-URLs and vice versa, as well as exposing a new endpoint on the API to support these queries.
- **Package URL Type Specificity**: Van Lindberg raised a question regarding the precedence of different Package-URL types, specifically when determining whether a "Git" type is preferable to other types like "GitHub" or "Software ID". Michael Herzog and Jon Moroney clarified that the general rule is to be as specific as possible regarding the software's location and identity, as more specific types like "GitHub" provide users with additional information such as associated issues and pull requests, whereas "Git" only indicates the protocol and operational shape.
- **Managing Package Personalities and Context**: The participants discussed the challenge of "package personalities," where the same code might exist across multiple platforms (e.g., GitHub, Docker, or npm). Michael Herzog and Jon Moroney explained that for Software Bill of Materials (SBOM) reporting, the key is identifying the source of the package—the upstream or downstream point of origin—rather than forcing a single type, as different contexts (binary vs. source) may require different representations.
- **PURL Test Schema Renaming Proposal**: Michael Herzog proposed changing the terminology for the two PURL test groups, currently named "base" and "advanced," to "required" and "recommended". This change is intended to align with the Conformance clause of the ECMA-427 standard (https://ecma-tc54.github.io/ECMA-427/#sec-conformance), where "required" maps to "shall" and "recommended" maps to "should".
- **PURL Test Schema Field Changes**: A proposal was presented to rename the "expected failure reason" field to "expected message" to allow for more nuanced feedback, such as information regarding normalization rules in the PURL type. This change would enable test cases to provide informative messages when normalization occurs, which is helpful for users even if the PURL remains technically valid.
- **PURL Test Schema Validation Type Proposal**: Michael Herzog recommended replacing the "roundtrip" test type with a "validate" test type. This change would shift the focus from merely checking if input and output are equal to allowing for the validation of non-canonical inputs, thereby providing more useful diagnostic messages.
- **PURL Test Schema Rollout Consensus**: The group discussed the implementation strategy for the proposed schema changes, with Philippe Ombredanne advocating for a two-step approach: first adopting the schema changes, and subsequently updating the test content. The participants agreed that Michael Herzog and John Horan would manage the release, including creating a version 1.1 release for the PURL specification repository to formalize these changes, while keeping the old version 0.1 tests available for reference.
- **Software ID Identification and Content Detection**: Philippe Ombredanne discussed the ongoing efforts to identify software without standard manifests, such as using content-based detection or small manifest files. The group noted that for registered packages, an extra lookup query is often required, and there is a need to help vulnerability database maintainers enrich their data with proper Package-URLs to improve identification accuracy.
- **Vulnerability Database and Common Platform Enumeration Limitations**: Jon Moroney and Philippe Ombredanne highlighted the significant challenges with the Common Platform Enumeration (CPE) system, noting that it lacks a consistent naming structure and is prone to drifting over time. The participants emphasized that the current system relies on manual, human-intensive disambiguation, and they are working on a project to create verified, canonical mappings between Common Vulnerabilities and Exposures (CVEs), Common Platform Enumeration, and Package-URLs.
- **Dependency Track and Release Management Integration**: Steve Springett updated the group on the Dependency Track community's plans to incorporate release management. The plan involves creating an open-source key server that supports the automatic submission of Software Identification tags, aiming to move away from the current system where software must have a known vulnerability before it can be effectively monitored.
- **Centralized Registry and Human Review Concerns**: The discussion addressed the potential "human problem" of flooding centralized registries with pull requests if automatic submission becomes the standard. Jon Moroney suggested that human review might serve as a necessary rate limiter, and Philippe Ombredanne pointed to the Nix package registry as a potential precedent for managing high-volume, bot-driven updates through automation and community oversight.
- **Service and Private Package-URL Types**: Van Lindberg inquired about the status of "service" and "private" Package-URL types, emphasizing the need for an internal identifier that helps large organizations map components within their architecture. While Michael Herzog and Steve Springett expressed some skepticism about making "private" a distinct type—suggesting it may be a dimension of existing types instead—they acknowledged the legitimate use case of identifying internal components that are otherwise "blind" due to the limitations of internal registries like Artifactory or Nexus.
- **PURL Identity and Artifact Attribution**: Van Lindberg argued that the standard logic for PURLs inverts the typical relationship between code and location, focusing on location rather than the identity of the code itself. Jon Moroney and Van Lindberg discussed the challenges of linking artifacts—such as MySQL or Java-packaged binaries in internal registries—back to their specific source code, noting that different packaging methods for the same underlying code create ambiguity.
- **Internal PURL Requirements**: Van Lindberg proposed adopting "private PURLs" within organizations to improve code identification. They argued that because various build "personalities" can obscure source root locations, creating a location-specific identifier would help teams trace back to the actual code that needs patching, specifically referencing the Log4j vulnerability found in internal Maven repositories.
- **Provenance versus Process Failure**: Steve Springett, Jon Moroney, Philippe Ombredanne, and Michael Herzog debated whether PURL identifiers could resolve the issue of provenance. The consensus was that the difficulty is primarily an organizational "process failure" rather than a technical one, as teams often struggle to maintain accountability for internal packages. Philippe Ombredanne cited an unnamed large US financial institution that tracks software via internal Debian packages as an example of a process-based solution rather than an identifier-based one.
- **PURL Qualifiers as an Alternative**: Michael Herzog suggested utilizing "qualifiers"—an existing component within the PURL specification—instead of creating new types for private repositories. They noted that while qualifiers might be less attractive because they appear at the end of the PURL, this option should be fully exhausted before introducing new PURL types, as the current proposal seemed like an "orthogonal problem".
- **Service Now Provenance Strategy**: Steve Springett shared the internal approach used at Service Now to address provenance failures. By defining team responsibilities within the platform and using build tools to dynamically generate configurations based on the specific team and repository, the organization achieved full provenance tracking. This approach shifted the focus from static configuration to dynamic, team-based build accountability.
- **Future of Software ID and Industry Involvement**: Philippe Ombredanne and Michael Herzog discussed the potential of the Software ID (SID) package type. They touched upon past efforts to involve Tom Alrich to energize commercial industry groups within the CycloneDX community. They noted that while those specific efforts had stalled, the goal remains to find a viable way to handle proprietary and commercial private software.
- **Historical Approaches to Open Source and Provenance**: This discussion highlighted how different organizations handle provenance, such as Oracle treating third-party code as first-party code within build pipelines, or Google utilizing a massive monorepo.
- **Organizational Process Realities and Shadow Git**: Philippe Ombredanne, Michael Herzog, and Steve Springett discussed how even well-architected systems often fail, leading to the creation of "Shadow Git" repositories. The group acknowledged that these workarounds are common when official processes do not meet the immediate needs of engineering teams, and they noted that consultants often play a role in identifying these organizational gaps.
- **Closing and Next Steps**: Michael Herzog concluded the meeting by scheduling the next session for two weeks later, with a separate Technical Group 2 (TC54-TG2) meeting occurring one week from Friday. Philippe Ombredanne confirmed that they are working on the pull request for the Software ID proposal so that it is ready for comments and reviews.
- The meeting was adjourned.
