  - Core specification updates and deprecations
    - Michael Herzog confirmed the completion of the Ecma review for PURL 2nd Edition.
    - A style guide is available in the community repository to assist with standardization.
    - Michael Herzog proposed introducing a new Go type to replace the existing version.
      - The team planned a deprecation path for the existing Golang type.
    - John Horan and Michael Herzog are overhauling the PURL test suite to conform with `purl-test.schema-0.2.json`.
  - gem.coop integration and specification alignment
    - Josef Šimánek introduced gem.coop (https://gem.coop/) as an alternative public Ruby gems repository.
    - gem.coop supports namespaces, unlike the global namespace design of RubyGems.
    - Repositories using custom namespaces should utilize the repository URL qualifier.
  - Virtual types and software-id implementation
    - Jaime Rodríguez-Guerra is advancing the virtual types proposal under PEP 804 (https://peps.python.org/pep-0804/).
    - Mapping virtual packages to concrete implementations will likely become necessary as adoption grows.
  - Git type and JSON comment syntax limitations
    - Jon Moroney discussed unescaped slashes and case sensitivity handling for the git type.
    - JSON files in the repository cannot support comments due to parser constraints.
    - Salve J. Nilsen proposed using JSONC to support comments, but broad adoption remains unfeasible.
  - software-id type prefix proposal
    - Salve J. Nilsen proposed omitting the type prefix and using a domain as a type.
    - Michael Herzog noted that modifying the type structure introduces a breaking change.
  - Package type definition and software-id handling
    - Philippe Ombredanne noted that the generic type acts as an escape hatch and should be replaced.
    - software-id provides a standardized identifier for general software not tied to a package manager.
    - Vulnerability management teams from Erlang, Apache, and the kernel plan to adopt software-id in CVE publications.
    - Philippe Ombredanne proposed exploring minimal package information via a manifest file at the root of software repositories.
  - Content-based discovery and tooling exploration
    - Philippe Ombredanne introduced Yara rules (https://virustotal.github.io/yara/) within AboutCode tooling to perform content-based discovery for unmanifested packages.
    - Content-based discovery serves as a stopgap method to identify package versions until manifests become standard practice.
  - Meeting scheduling and international participation
    - Jonatan Männchen announced absence through December due to relocating to Indonesia in the UTC+8 time zone.
    - Philippe Ombredanne suggested exploring additional time slots next year to accommodate participants in Asian time zones.
- **Introduction of gem coop**: Philippe Ombredanne opened the meeting with a code of conduct reminder and welcomed a new participant, Josef Šimánek, who represents an alternative public Ruby gems repository called gem.coop (https://gem.coop/). Josef Šimánek explained that their project allows users to upload gems for free without registration or login requirements, setting gem.coop apart from GitHub packages or Google artifact repositories which require accounts. Josef Šimánek noted that gem.coop features name spacing, a feature new to the Ruby community that current specifications do not account for, and expressed a desire to integrate PURLs generically for the Ruby ecosystem.
- **FOSDEM and Community Events Announcements**: Philippe Ombredanne announced upcoming events for the end of January, including FOSDEM, a packaging dev room, and a Code-organized workshop scheduled for the Monday following FOSDEM. Additionally, Philippe Ombredanne highlighted "FOSSapalooza," an event organized by Adam Herzog to bring together organizations from OpenSSF, Eclipse, and the Linux Foundation to co-sponsor and co-organize an event the day before FOSDEM. Participants were encouraged to submit talks and sponsor the events.
- **Core Team Updates on PURL and VERS Specifications**: Michael Herzog provided updates on specifications, stating that the Ecma review of the editorial side for PURL 2nd Edition and VERS 1st Edition is complete. Releases will be tagged using the edition as the version for Ecma TC54 repositories, while traditional version numbers will be maintained for PURL and VERS specifications. Michael Herzog noted that a community style guide has been established to align with Ecma and ISO fast-track standards. Furthermore, Michael Herzog reported that discussions during the TG2 meeting led to a tentative decision regarding the Golang PURL type: a new PURL type named 'go' will be introduced to handle modern Go ecosystem conventions, while the existing 'golang' type will be placed on a deprecation path to resolve long-standing naming issues.
- **Test Suite Overhaul and Structure**: Michael Herzog and John Horan discussed an ongoing major overhaul of the PURL test suite led by Michael and John to conform with `purl-test.schema-0.2.json`. Michael Herzog highlighted an open structural issue concerning whether to maintain test case identifiers within current test files or adopt an "atomic option" where each file contains a single test case with uniqueness given by the full file path.
- **Git PURL Type Bug Fixes and Case Sensitivity**: Jon Moroney raised issues regarding the PURL git type, specifically concerning percent-encoding slashes in repository path examples and whether URLs should be case-sensitive. Jonatan Männchen argued that URLs must remain case-sensitive since casing can change path meanings. Philippe Ombredanne and Jonatan Männchen agreed that the git type should remain case-sensitive and that tests should be corrected accordingly, while noting that future editions should eliminate the requirement to percent-encode forward slashes. Jon also attempted to add comments to JSON files, leading to a discussion on valid JSON formatting.
- **JSON Comment Syntax and Testing Workflows**: Salve J. Nilsen suggested utilizing the proposed jsonc.org (https://jsonc.org/) specification for JSON with comments, but Jonatan Männchen, Michael Herzog, and Philippe Ombredanne agreed that standard JSON parsers do not support comments and adopting JSONC is impractical due to parser limitations and standard tool compatibility. Jon Moroney discussed adding a GitHub action for basic JSON parsing verification, though Jonatan Männchen noted Jon's workflow actions had not been approved to run yet. Philippe Ombredanne pointed out existing repository checks like `make check`, `make conf`, and `make gendocs`.
- **gem.coop Integration and Namespace Mapping with PURLs**: Josef Šimánek shared screen examples of implementing PURLs for gem.coop, noting that gem.coop incorporates namespaces and stores artifacts across separate host sources rather than a single global repository. Michael Herzog and Jonatan Männchen clarified that the repository URL should not be part of the namespace, but rather appended as a global qualifier (`repository_url`), referencing Annex B of the ECMA 427 2nd Edition standard (https://ecma-tc54.github.io/ECMA-427/#sec-recommended-qualifiers). Josef Šimánek acknowledged this feedback, confirming they will submit a pull request with appropriate examples and test documentation to ensure gem.coop is correctly discoverable for tooling and ecosystem index builders.
- **Virtual Types and software-id PURLs**: Jaime Rodríguez-Guerra and Philippe Ombredanne discussed virtual types (referenced in PEP 804 - https://peps.python.org/pep-0804/) and software-id types, noting potential conceptual overlaps. Jaime Rodríguez-Guerra urged the team to review and merge their pending pull requests before the end of the year to align with funding schedules starting in 2027. Philippe Ombredanne and Jaime Rodríguez-Guerra agreed that mapping virtual types to concrete packages will naturally emerge once the implementation is actively used.
- **software-id PURL Proposal and Discussion on Omitting Types**: Salve J. Nilsen brought up a previous proposal regarding software-id PURLs where the type is omitted or replaced directly by a domain, using a leading slash to indicate an empty type prefix. Michael Herzog and Philippe Ombredanne objected, stating that altering the type structure is a major breaking change that is not feasible for the near term, while Salve J. Nilsen clarified that the leading slash was intentionally proposed to prevent field ambiguity.
- **Package-URL Type Definitions and Unknown Formats**: Discussed by Philippe Ombredanne, Michael Herzog, and Salve J. Nilsen, the participants addressed the validity of Package-URLs containing slashes after colons and the necessity of defining artifact types (such as gems, CPAN tarballs, or Debian packages) even when formats are unrecognized. Philippe Ombredanne proposed a domain-specific system where domains broadcast type definitions via JSON Schemas, while Salve J. Nilsen emphasized that type descriptions remain essential to specify artifact appearance, repository ecosystem, and download criteria regardless of whether a standard format is followed.
- **Content-Based Codebase Discovery Tools**: Philippe Ombredanne and Michael Herzog explored utilizing content-based discovery tools from the AboutCode project to identify unstructured codebases, such as the Linux kernel (specifically citing version 2.6.8) or Zlib OpenSSL, which lack traditional directory markers. By combining this content scanning with configuration conventions like `meta.json` at the root directory, developers can establish minimal package metadata for software that lacks structured ecosystem manifests.
- **Vulnerability Management Adoption and CVE Backfilling**: Philippe Ombredanne, Jonatan Männchen, and Salve J. Nilsen discussed industry buy-in for Package-URLs, noting adoption by vulnerability management teams across the Linux kernel, Apache, and Erlang organizations for use in published CVEs. Philippe Ombredanne shared that Greg Kroah-Hartman expressed intent to backfill every historical kernel CVE with a Package-URL, while Jonatan Männchen and Salve J. Nilsen noted the utility of tracking pervasively bundled, unmanifested software components like the compression code that recently broke across environments.
- **Naming Conventions and Software Identifier Terminology**: Salve J. Nilsen, Jonatan Männchen, Jon Moroney, Michael Herzog, and Philippe Ombredanne debated the terminology used for package identifiers, specifically evaluating the software-id designation and the elimination of the generic type escape hatch. Salve J. Nilsen raised concerns that inconsistent naming could provoke criticism from meticulous maintainers, while Jon Moroney and Michael Herzog argued that engagement and education opportunities outweigh minor naming discrepancies, ultimately driving developers away from generic classifications toward more specific package types.
- **AboutCode Purl Registry and Yara Rule Integration**: Philippe Ombredanne, Michael Herzog, Salve J. Nilsen, and Jonatan Männchen reviewed the PURL registry initiative on GitHub (https://github.com/package-url/purl-registry), which utilizes Yara rules (https://virustotal.github.io/yara/) - a programmable pattern matching engine functioning like a virus scanner—to identify packages lacking manifests and version metadata. Philippe Ombredanne noted that Yara rules are currently written in Python with plans for a Rust version, enabling decentralized and distributed matching that complements manual manifests and cryptographic signing approaches.
- **Participant Availability and Schedule Adjustments**: Jonatan Männchen, Philippe Ombredanne, Michael Herzog, Salve J. Nilsen, Josef Šimánek, and John Horan discussed participant time zones across Central European time, California, and Jonatan Männchen's relocation to Indonesia at UTC plus 8 until the end of December. Philippe Ombredanne concluded that the team will focus on the Erlang package type during upcoming meetings over the final six weeks of the year while accommodating participant availability.
- The meeting was adjourned.
