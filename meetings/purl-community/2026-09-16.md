- **Approval of Previous Meeting Minutes**: Michael Herzog welcomed participants to the PURL community call operating under the TC54 code of conduct, noting that meetings are recorded to generate human-in-charge minutes. John Horan provided the latest minutes in the chat, and with no objections raised by attendees, Michael Herzog recorded the September 2 minutes as approved.
- **Conda Package Manager Integration and PURL Types**: Philippe Ombredanne reported that the OSI's Clearly Defined project is adopting PURL, but noted that a contributor working on the PURL converter found Conda coordinates to be problematic and difficult to use with PURL definitions. Michael Herzog and Philippe Ombredanne discussed an ongoing Conda Enhancement Proposal involving Jaime Rodríguez-Guerra and the Conda Forge community, outlining three primary Conda use cases: building an index of packages, examining an installed Conda installation, and passing a PURL to a Conda package manager. Additionally, Philippe Ombredanne highlighted tensions regarding Anaconda restricting their security feed for open-source packages to commercial customers , prompting a volunteer-driven side project to create an open-source Conda package feed.
- **Go PURL Type Structural Issues**: Michael Herzog identified Go as having high-priority open issues among frequently used PURL types due to fundamental structural challenges regarding go modules. Jon Moroney asked about how to investigate these issues, and Michael Herzog directed them to look up the issue label "PURL type go," which encompasses approximately eight overlapping issues in the repository.
- **PURL 2nd Edition and VERS 1st Edition Updates**: Michael Herzog provided updates on PURL 2nd Edition, noting minor changes ready for pull requests on the ECMA-427 website repository (https://github.com/Ecma-TC54/ECMA-427), a new version 1.1 of the PURL type definition schema, and a release notes document added to the repository. Michael Herzog and Steve Springett discussed the VERS 1st Edition transition from draft source documents in the vers-spec repository to the ECMA-xxx-VERS repository (https://github.com/Ecma-TC54/ECMA-xxx-VERS), noting that a TC54 meeting the following day served as a gating checkpoint for approval while allowing subsequent editorial fixes (such as paging issues identified by Jan Kowalleck) over the coming weeks.
- **ECMA-427 Repository Branching and Ecmarkup**: John Horan explained that they forked the upstream ECMA-427 repository and organized changes into six separate branches corresponding to each clause of the specification, alongside providing GitHub diff URLs. Steve Springett confirmed that following a positive vote at the TC54 meeting, John Horan and Michael Herzog have permission to merge those branches. John Horan described several challenges of learning Ecmarkup (a strict HTML dialect with automatic numbering), while Steve Springett clarified that numbering is handled automatically, requiring manual removal from input markdown files.
- **Erlang OTP Versioning Objections to the VERS Specification**: Jonatan Männchen stated their intention to vote against the proposed VERS specification at the upcoming TC54 meeting, arguing that it fails for the Erlang OTP ecosystem because version comparisons can be undefined due to encoded branching logic. Jonatan Männchen pointed out that constraints requiring a global canonical order based on version sorting cannot be fulfilled by Erlang versions, where comparing versions from different branches yields an undefined result in the OTP comparison algorithm. Philippe Ombredanne and Steve Springett noted that version comparison logic is orthogonal to the core VERS specification and should be handled by type-specific rules or escape hatches.
- **Linear Versus Tree Version Structures in VERS**: Jonatan Männchen argued that the core problem with VERS is its limitation of compressing version ranges into a linear string, failing to model tree or graph structures like Git commits with multiple branches and patch SHAs. Steve Springett noted that CycloneDX previously recognized this limitation and allows multiple VERS strings to handle complex component ranges. Jon Moroney added that the GitHub advisory database decomposes complex version ranges into sets of multiple version ranges, and suggested documenting the algorithm, calling out undefined states, and providing guidance for security advisories.
-  **Scope Clarification for VERS 1st Edition**: Michael Herzog emphasized the impending voting deadline and noted that VERS was intentionally designed as a compact, linear string notation. To address Jonatan Männchen's concerns without blocking the 1st Edition, Steve Springett and Michael Herzog proposed updating the scope section of the VERS specification to explicitly state that it applies only to globally sorted, linear version types and excludes tree or graph structures. Jonatan Männchen agreed that restricting the scope to globally ordered versions would make the specification consistent and allow their ecosystem to operate outside of it cleanly.
- **TC54 General Assembly Reporting and Future Workarounds**: Steve Springett recommended that TC54 co-chairs, including Chris de Almeida, include this direction in their chair's report for the general assembly to formally recognize the VERS standard's scope. Philippe Ombredanne discussed potential future workarounds for version trees, such as prefixing versions with branch paths or using set operations. Michael Herzog committed to drafting the scope update for the spec.html file in the ECMA-xxx-VERS repository and Philippe Ombredanne created a GitHub issue to capture version tree structures for future editions.
- **Vulnerability Versioning and Version Branches**: Philippe Ombredanne discussed how vulnerabilities fixed across different version branches can function almost like entirely separate products or components due to significant code changes. Jon Moroney proposed compiling a list of real-world examples to determine if a single solution or multiple solutions are required. Steve Springett suggested that Jonatan Männchen demonstrate their set and union approach during the upcoming community call. Jonatan Männchen and Steve Springett highlighted the difficulty of maintaining backward compatibility and representing hierarchical trees as flat strings, with Jonatan Männchen noting they documented various package manager oddities in a GitHub fork of VERS. Michael Herzog concluded that the group will work on these issues ahead of the TC54 meeting to eventually refocus on software identification.
- **Software Identification and Proposed PURL Rule Changes**: Jon Moroney shared an update regarding a proposed rule change in the Common Vulnerabilities and Exposures (CVE) world, driven by a former high-ranking official from CISA, which would effectively require the use of a Package-URL (PURL). Jon explained that maintaining a software identification standard would ensure a PURL type is appropriate for nearly every scenario. Steve Springett noted that hardware use cases represent an exception that requires a separate PURL type.
- **Open Source Types and Community Event Discussions**: Jon Moroney mentioned discussing the Git type at Defcon, noting it establishes a baseline where an appropriate type is consistently available for open-source projects. Philippe Ombredanne shared that an upcoming presentation titled "PURL Power" will be given at the "India FOSS" conference in India. This prompted Steve Springett and Philippe Ombredanne to humorously discuss organizing a conference named "PURL Con". Michael Herzog and other participants briefly addressed logo design tasks and a lighthearted mention by Philippe Ombredanne regarding a trademark for "PURL" before Michael Herzog thanked everyone and adjourned the meeting.
- The meeting was adjourned.
